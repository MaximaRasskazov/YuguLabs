# Загрузка аватара в профиль — что и куда добавили

Документ объясняет реализацию загрузки фото профиля (аватара): какое
решение приняли, какие файлы затронули и как это проверить.

## 0. В двух словах

- **Что за задача.** Дать пользователю загрузить фото профиля (аватар),
  показывать его в шапке и панели профиля, уметь удалить. Это **не отдельная
  лаба-ТЗ**, а доработка профиля — описана отдельно от лабы по логированию.
- **Что надо было сделать.** Хранилище аватаров, загрузка/удаление через API,
  публичная отдача картинки для тега `<img>`, валидация размера и типа **на
  сервере**, показ в UI и сохранение между сессиями.
- **Что сделали.** Таблица `user_avatars` (`BYTEA` + MIME), ручки
  `POST`/`DELETE /api/me/avatar` и публичная `GET /api/users/{id}/avatar`,
  валидация по сигнатуре файла, проводка `avatar_url` в `/auth/me`, загрузка в
  панели профиля, тест валидации.
- **Что изменилось по ходу.** Кнопку загрузки сначала положили в
  `ProfilePage.vue`, но эта страница **не подключена в роутере** (мёртвый
  компонент) — реальная панель профиля это `ProfilePanel.vue` (открывается
  кликом по аватару в шапке), туда и перенесли рабочую загрузку.

## 1. Цель

Дать любому пользователю (студент, преподаватель, деканат, админ) загрузить
своё фото в профиле, увидеть его в шапке и карточке профиля, при желании
удалить. Фронт уже был частично готов (в шапке и профиле выводился
`avatar`), но бэкенда, хранилища и загрузки не было — добавили всё это.

## 2. Как храним и почему

Аватар хранится **в базе данных** (PostgreSQL), в отдельной таблице
`user_avatars` (бинарь `BYTEA` + MIME-тип).

Почему так:

- **Отдельная таблица, а не колонка в `users`** — чтобы бинарные данные не
  тянулись в каждом `SELECT *` по пользователям (вход, списки студентов,
  отчёты). Аватар читается только когда его реально запрашивают.
- **В БД, а не на диске/в S3** — не нужно поднимать отдельный том или
  объектное хранилище: фото переживает перезапуск контейнеров (живёт в
  томе PostgreSQL) и автоматически попадает в дампы/бэкапы БД. Для системы
  такого масштаба это самый простой и надёжный вариант.
- Ограничения: размер ≤ 2 МБ, типы JPEG/PNG/WebP. Тип определяется по
  **сигнатуре файла** на сервере, а не по присланному заголовку — нельзя
  подсунуть произвольный файл под видом картинки.

  Где в коде (файл [`backend/internal/service/auth/avatar.go`](../backend/internal/service/auth/avatar.go)):
  - проверка типа по сигнатуре — `http.DetectContentType(content)` на **строке 54**,
    сверка с белым списком на **строках 55–56**;
  - сам белый список MIME `allowedAvatarTypes` (jpeg/png/webp) — **строки 24–28**;
  - проверка размера ≤ 2 МБ — **строка 51** (константа `MaxAvatarBytes`, объявлена на **строке 19**).

  Всё это — в методе `SetAvatar` (строки 47–57), который вызывается из
  HTTP-обработчика загрузки до сохранения в БД.

## 3. Поток данных (как это работает)

1. Пользователь на странице профиля выбирает файл → фронт отправляет
   `multipart` на `POST /api/me/avatar` (с токеном).
2. Бэкенд проверяет размер и тип, сохраняет байты в `user_avatars`
   (upsert — одно фото на пользователя).
3. В ответ приходит `avatar_url` вида `/api/users/{id}/avatar?v=<версия>`.
4. `<img>` в шапке и профиле грузит картинку с этого **публичного** GET-адреса
   (публичный — потому что тег `<img>` не умеет слать токен авторизации;
   аватар не относится к чувствительным данным).
5. При входе `GET /api/auth/me` возвращает `avatar_url`, если фото есть, —
   чтобы оно показывалось сразу после логина и переживало перезагрузку.

## 4. Изменения на бэкенде (Go)

| Файл | Что добавили |
|------|--------------|
| `backend/sql/migrations/00026_create_user_avatars.sql` | Таблица `user_avatars` (user_id, content, content_type, updated_at) |
| `backend/sql/queries/user_avatars.sql` | SQL-запросы: upsert / получить / метаданные / удалить |
| `backend/internal/repo/queries/*` (сгенерировано sqlc) | Код доступа к БД для этих запросов |
| `backend/internal/service/auth/avatar.go` | Бизнес-логика: валидация (размер/тип), `SetAvatar` / `GetAvatar` / `DeleteAvatar` |
| `backend/internal/service/auth/service.go` | В `Me()` добавлен признак наличия аватара (для `avatar_url`) |
| `backend/internal/transport/http/handler/avatar.go` | HTTP-обработчики: загрузка, удаление, отдача картинки |
| `backend/internal/transport/http/handler/auth.go` | `Me()` отдаёт `avatar_url` |
| `backend/internal/transport/http/handler/errors.go` | Понятные коды ошибок (слишком большой / неверный тип / не найден) |
| `backend/internal/transport/http/dto/auth.go` | Поля `avatar_url` и ответ загрузки |
| `backend/internal/transport/http/router.go` | Роуты (см. ниже) |
| `backend/internal/service/auth/avatar_test.go` | Тест валидации (пустой/не картинка/слишком большой) |

### API-эндпоинты

| Метод | Путь | Доступ | Назначение |
|-------|------|--------|-----------|
| POST | `/api/me/avatar` | авторизованный | Загрузить фото (multipart, поле `avatar`) |
| DELETE | `/api/me/avatar` | авторизованный | Удалить своё фото |
| GET | `/api/users/{id}/avatar` | публичный | Отдать картинку для `<img>` |

| `frontend/src/views/ProfilePage.vue` | Та же загрузка, но компонент **не подключён в роутере** (`router/index.js`) — оставлен как запасной/неиспользуемый, рабочая версия в `ProfilePanel.vue` |

## 6. Инфраструктура

- `frontend/nginx.conf` — поднят `client_max_body_size` до 4 МБ для `/api/`
  (дефолт nginx — 1 МБ, иначе загрузка фото >1 МБ отклонялась бы прокси).

## 7. Как проверить

1. Пересобрать и поднять стек:
   ```bash
   APP_PORT=8080 docker compose up -d --build
   ```
   (миграция `00026` применится при старте бэкенда автоматически).
2. Войти под любым сид-аккаунтом (студент / преподаватель / деканат / админ).
3. Профиль → кликнуть по аватару → выбрать картинку (JPEG/PNG/WebP до 2 МБ).
4. Фото появляется в профиле и в шапке; «Удалить фото» убирает его.
5. Негативные проверки: файл >2 МБ или не-картинка → понятная ошибка.

## 8. Замечание по деплою (для код-ревью)

Миграция намеренно пронумерована `00026`, хотя в `develop` последняя —
`00024`. Номер `00025` занят параллельной веткой восстановления пароля
(`feat/password-reset`). Чтобы при слиянии обеих веток не возникло дубля
версии в goose, эту фичу нужно мёржить **после** ветки восстановления
пароля (или согласовать перенумерацию).
