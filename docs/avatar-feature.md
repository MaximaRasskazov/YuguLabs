# Фотография профиля (лаба «работа с файлами»)

Единый документ по фиче загрузки фотографии профиля: что сделано, как
устроено, и **ответы на «простые» продакшн-вопросы** (анти-спуфинг, сжатие,
архив и т.д.). Рядом лежит runnable-сценарий [avatar.http](avatar.http) для
VS Code REST Client.

Методичка написана под Laravel (таблица `files`, Intervention Image, диск
`storage/app`). Проект — Go (chi + pgx + sqlc) + Vue, поэтому реализован
**эквивалент** на текущем стеке (в ТЗ это допускается).

---

## TL;DR — что делает фича

Из одного загруженного снимка сервер делает **две производные**:
1. **сжатую копию оригинала** (даунскейл ≤1600px + перекодирование) — отдаётся
   только владельцу через защищённый маршрут;
2. **аватар 128×128** — публичная миниатюра для `<img>`.

Исходные «тяжёлые» байты не хранятся — только сжатая копия. Всё лежит в БД
(bytea), поэтому у файлов нет публичного URL.

Три акцента, которые особо проверяет преподаватель: **(1)** проверка по
содержимому, а не по имени; **(2)** сжатие/даунскейл 4K; **(3)** хранение
сжатой копии. Все три — ниже в FAQ.

## FAQ — продакшн-вопросы и ответы

### 1. Как точно проверяем, что это настоящее изображение, а не текстовый/зашифрованный файл, переименованный в `.png`? (по содержимому, не по имени)

Мы **не верим ни имени файла, ни заголовку `Content-Type`** от клиента. Тип
определяется **реальной попыткой декодировать байты**:

- `image.DecodeConfig(bytes)` — читает заголовок-сигнатуру формата (магические
  байты + структуру) и габариты, **не распаковывая** всю картинку;
- `image.Decode(bytes)` — полная распаковка в пиксели.

Файл должен быть валидным **JPEG / PNG / WebP по своим байтам**. Текст, exe или
зашифрованный блоб, переименованный в `.png`, **не образует валидной структуры
изображения** → `DecodeConfig`/`Decode` возвращает ошибку → ответ **415**.

> Код: [`backend/internal/imageutil/imageutil.go`](../backend/internal/imageutil/imageutil.go),
> функция `Process` (сначала `DecodeConfig`, затем `Decode`).

**Почему не `http.DetectContentType`?** Это «sniff» первых 512 байт — его можно
обмануть, прилепив PNG-магию в начало мусора. Полный декод строже: содержимое
должно реально развернуться в пиксели, иначе отказ.

### 2. А если подменили только расширение/свойства, но внутри настоящая картинка?

Тогда это **и есть настоящая картинка** — мы её примем. Смысл проверки —
отсечь **не-изображения**, а не наказывать за «неправильное» расширение. Формат
хранения мы определяем сами по результату декода, а не по имени файла. Имя,
которое прислал клиент, сохраняем только как метаданные (`original_name`).

### 3. Зашифрованный `.png` пройдёт?

Нет. Зашифрованные/произвольно сжатые байты не образуют валидный
JPEG/PNG/WebP-поток → `DecodeConfig` падает → **415**. Пройдёт только то, что
реально декодируется как изображение.

### 4. Что происходит с 4K-снимком? Где сжатие?

Снимок крупнее **1600px** по большей стороне **даунскейлится** с сохранением
пропорций и **перекодируется** (JPEG q82; PNG — только если у исходника есть
альфа-канал). Хранится сжатая копия, а не исходные байты.

> Живой прогон: `4000×3000, 274 КБ` → сохранено `1600×1200, 42 КБ` (≈6.5× меньше).

### 5. Защита от «бомбы» (крошечный файл — гигантское разрешение)?

До полной распаковки читаем габариты из заголовка (`DecodeConfig`) и режем по
лимиту **40 Мп**. Гигапиксельный PNG (который в распакованном виде съел бы всю
память) **не доходит до декода** → **413**. Покрыто юнит-тестом
`TestProcess_RejectsPixelBomb`.

### 6. Где хранятся файлы и почему нельзя скачать оригинал по прямому URL?

В **БД** (`user_photos`, тип `bytea`), а не на диске с публичным URL. У файла
**нет URL вообще** — его физически нельзя запросить напрямую. Оригинал отдаётся
**только владельцу** через контроллер с проверкой (`GET /api/photo/download`).
Публична лишь миниатюра 128×128. Это и есть «защита от прямого доступа» из ТЗ.

Бонус хранения в БД: переживает рестарт контейнеров (живёт в томе PostgreSQL) и
попадает в дампы/бэкапы — отдельный том/S3 не нужен.

### 7. Что именно хранится и в каком качестве?

Две производные на одну фотографию:
- `original_content` — **сжатая копия** (≤1600px, перекодированная, q82);
- `avatar_content` — **аватар 128×128**.

Исходные «тяжёлые» байты **не сохраняются** — только сжатая копия (ровно как
советовал преподаватель: «делают сжатую копию исходного изображения и хранят
её»).

### 8. Есть ли ручка «посмотреть и скачать все фото»? В каком качестве?

Да, две:
- **Посмотреть все** — `GET /api/photo/all` (только админ, право
  `photos.export`): JSON-список метаданных всех активных фото (кто, имя файла,
  формат, размер, габариты, дата) + `avatar_url` миниатюры для просмотра.
- **Скачать все** — `POST /api/photo/archive` (только админ): ZIP с
  `originals/` (**сжатые копии**), `avatars/` (128×128) и `registry.xlsx`
  (реестр: ID, ФИО, email, группа, дата, имя файла в архиве, путь-локатор).

**Качество = сжатые копии** (что храним — то и в архиве). Мягко удалённые фото
в список и архив не попадают.

### 9. Сколько фотографий на пользователя? Мягкое удаление?

Ровно **одна активная** (частичный уникальный индекс `WHERE deleted_at IS
NULL`). При загрузке новой прежняя **мягко удаляется** (`deleted_at`) —
восстановимо, история сохраняется. `DELETE /api/photo` — тоже мягкое (идемпотентно).

### 10. Логируются ли действия с фото?

Да — в `change_logs` с `entity_type = user_photo` (отдельно от истории профиля,
чтобы не засорять журнал users/roles/permissions).

### 11. Известное ограничение — EXIF-ориентация

Go-декодер JPEG **игнорирует EXIF orientation**: портретное фото с телефона
может сохраниться повёрнутым. Для лабы некритично; при необходимости добавляется
разбор EXIF перед ресайзом.

## Хранилище и таблица

Таблица `user_photos` ([миграция 00028](../backend/sql/migrations/00028_create_user_photos.sql)):
`original_content`/`avatar_content` (bytea) + метаданные (`original_name`,
`description`, `format`, `size_bytes`, `width`, `height`) + `deleted_at`
(мягкое удаление). Старая таблица одиночных аватаров `user_avatars` удалена
(её роль поглощена `user_photos`).

> ⚠️ Деплой на живой стенд: миграция `00028` делает `DROP user_avatars` —
> уже загруженные ранее аватары будут утеряны, пользователям нужно перезалить
> (теперь они хранятся в `user_photos`).

## Пайплайн загрузки

`POST /api/photo` (поле `photo`) → `MaxBytesReader` (≤16 МБ тела) →
`imageutil.Process` (анти-спуфинг + лимит пикселей → даунскейл/сжатие → аватар
128×128) → в одной транзакции: мягко удалить прежнюю активную, вставить новую,
записать действие в `change_logs` → ответ `PhotoResponse` (метаданные +
`avatar_url` + `download_url`).

4K→1600×1200 (42 КБ из 274 КБ), аватар 128×128 (image/jpeg), скачивание
оригинала, анти-спуфинг (415), список всех фото (403 не-админ / 200 админ),
архив (ZIP с originals/avatars/registry.xlsx), удаление (204→404).

## Ручной сценарий (REST Client)

Готовый пошаговый сценарий — [avatar.http](avatar.http): логин → загрузка →
**текст под видом `image/png` → 415** → метаданные → публичная миниатюра →
скачивание оригинала → список всех (админ) → архив → удаление → 404.
Для шага загрузки нужен файл-образец `avatar-sample.png` рядом с `.http`.
