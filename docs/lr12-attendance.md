Единый документ по лабораторной работе №12: **что требовалось по ТЗ**, **что
и как мы сделали**, и **ответы на вопросы, которые задаст преподаватель на
защите**. Рядом лежит runnable-сценарий
[lr12-attendance.http](lr12-attendance.http) для VS Code REST Client и два

  вручную «испортить» одну (например, дату на `23-09-2024`) и продемонстрировать,

## TL;DR — что делает фича

Эндпоинт **`POST /api/attendance/calculate`** принимает Excel-файл `.xlsx` с
посещаемостью, и:

1. **парсит** лист «Посещаемость» (колонки ищет по имени, не по позиции);
2. **считает** по каждому студенту процент посещаемости и сданных лаб;
3. **определяет** зачёт: авто-зачёт **или** (посещаемость ≥ порога **и** лаб ≥
   нужного минимума);
4. **группирует** по учебным группам и считает success/unsuccessfully;
5. **возвращает** JSON строго по формату из ТЗ + дополнительный плоский список
   `automatic_success_students`.

Доступ — только у админа (право `calculate-attendance`). База данных в расчёте
**не участвует**: на вход байты файла, на выход — JSON.

## Куда уходит результат и как показать, что всё работает

**Результат никуда не сохраняется** — он возвращается **прямо в теле HTTP-ответа**
(код 200, `Content-Type: application/json`). Это синхронная операция «загрузил
файл → сразу получил расчёт». В БД/файл ничего не пишется — лаба чисто файловая,
так задумано по ТЗ (на вход xlsx, на выход JSON).

**Как показать на защите** — через REST Client (расширение VS Code, файл
[lr12-attendance.http](lr12-attendance.http)):

1. Открой `lr12-attendance.http`, запусти **#1 (login)** — получишь токен админа.
2. Запусти **#2** с файлом [attendance-sample.xlsx](attendance-sample.xlsx) —
   увидишь в панели справа **код 200 и весь JSON-отчёт** (группы, проценты,
   `result`, итоги, `automatic_success_students`). Это и есть доказательство.
3. Запусти **#2-bis** с [attendance-synonyms-demo.xlsx](attendance-synonyms-demo.xlsx) —
   покажет, что понимаются разные записи флагов (`1/да/yes/+/true`).
4. Дальше шаги **#3–#6** показывают коды ошибок: 401 (без токена), 403 (не админ),
   400 (нет файла), 422 (не .xlsx).

**Чтобы доказать, что проверки реальны:** открой демо-файл в Excel, поменяй дату в
одной строке на `23-09-2024` (через дефис), сохрани и отправь снова → получишь
**422** с текстом «дата должна быть в формате ДД.ММ.ГГГГ, получено: «23-09-2024»»
и **номером строки**.

## Как это работает под капотом (поверхностно — то, что препод смотрит глазами)

Три класса, по одному файлу, конвейер `Parse → Calculate → Build`:

**1. Парсер** [`parser.go`](../backend/internal/service/attendance/parser.go) —
читает книгу через excelize, находит лист «Посещаемость», строит карту «заголовок
→ номер колонки» (поэтому колонки можно переставлять), затем нормализует каждую
строку. Здесь же — все проверки данных, которые удобно показать:

- **Число строк** (защита от xlsx-бомбы): сразу после `GetRows` —
  `if len(rows)-1 > maxDataRows { ... ErrTooManyRows }` (потолок 200 000). Препод
  любит «а если файл на миллион строк» — вот ответ.
- **Дата — регуляркой**: `dateRe = regexp.MustCompile(`^\d{2}\.\d{2}\.\d{4}$`)` —
  строго ДД.ММ.ГГГГ. «23-09-2024» не матчится → ошибка с номером строки.
- **Время — регуляркой**: `timeRe = ...^\d{2}:\d{2}$`.
- **Тип занятия**: только `lect` или `lab`, иначе ошибка.
- **Флаги (Посещение, Зачёт автоматом)**: `parseFlag` принимает синонимы
  `1/0, да/нет, yes/no, true/false, +/-`; чужое значение → ошибка.
- **Числа**: `parseInt` понимает и `5`, и Excel-формат `5.0`.
- **Подгруппа**: пустая → 1.

**2. Калькулятор** [`calculator.go`](../backend/internal/service/attendance/calculator.go) —
один проход по строкам: собирает множество **уникальных занятий**
(ключ `дата|время|тип|номер`, без группы — занятие у двух групп считается одним),
агрегирует данные по студентам, потом для каждого считает процент посещения и
лаб, выставляет `result` и группирует. Сортировки (занятия по дате/времени,
группы и студенты по имени) — чтобы JSON был стабильным.

**3. Построитель ответа** [`builder.go`](../backend/internal/service/attendance/builder.go) —
собирает финальную структуру и плоский список `automatic_success_students`.

**Хендлер** [`handler/attendance.go`](../backend/internal/transport/http/handler/attendance.go)
тонкий: режет размер тела (`MaxBytesReader`), проверяет наличие файла и
расширение `.xlsx`, зовёт сервис, маппит ошибки в HTTP-коды.

## Формат входного файла

Лист **«Посещаемость»**, первая строка — заголовки. Обязательные колонки:
`Группа`, `ФИО`, `Дата` (ДД.ММ.ГГГГ), `Время` (ЧЧ:ММ), `Тип занятия`
(`lect`/`lab`), `Номер занятия`, `Посещение` (0/1), `Выполнено лаб` (целое).
Необязательные: `Подгруппа` (пусто → 1), `Зачёт автоматом` (пусто → 0).

**Колонки ищутся по имени, а не по позиции** — их можно переставлять, и файл не
сломается (есть тест `TestParser_ColumnOrderIndependent`).

## Правила расчёта (точно как в ТЗ)

- **Уникальное занятие** = ключ `дата | время | тип | номер`. Группа в ключ
  **не входит**: одно и то же занятие у разных групп/подгрупп — это **одно**
  занятие.
- **Всего занятий** = число уникальных занятий по всему файлу.
- **Посещено** = число занятий студента с отметкой `visit = true`.
- `visit_percent = round(посещено / всего × 100)`.
- `success_labs` = «Выполнено лаб» (из колонки).
- `success_labs_percent = round(success_labs / REQUIRED_LABS × 100)` (может быть
  > 100%).
- `result = true`, если **авто-зачёт** = 1 **ИЛИ** (`visit_percent ≥
  ATTENDANCE_PERCENT_THRESHOLD` **И** `success_labs ≥ REQUIRED_LABS`).
- Итоги группы: `success` — студентов с `result=true`, `unsuccessfully` —
  остальные.
- `leasons` отсортированы по дате и времени по возрастанию; группы — по имени.

## FAQ — вопросы защиты и ответы

### 1. Почему лаба написана под Laravel, а у вас Go? Это засчитывается?

Да. ТЗ прямо разрешает альтернативные инструменты. Проект изначально на Go —
переписывать его на PHP ради одной лабы бессмысленно и неправильно. Мы
реализовали **точный функциональный эквивалент**: те же параметры конфигурации,
тот же маршрут и право, та же бизнес-логика, тот же формат JSON, разбиение на
три класса по SRP, DTO, тесты. Это тот же подход, что и в предыдущей лабе про
аватар (она так и была зачтена).

### 2. Как определяется «уникальное занятие»? Почему группа не в ключе?

Ключ занятия — `дата|время|тип|номер` (см. `lessonKey` в
[`calculator.go`](../backend/internal/service/attendance/calculator.go)). Группа
**намеренно** не в ключе: по ТЗ одно занятие может проводиться для нескольких
групп/подгрупп, но в файле представлено отдельными строками. Если бы группа
входила в ключ, одно лекционное занятие для двух групп посчиталось бы как два —
и знаменатель посещаемости был бы завышен. Тест:
`TestCalculate_SameLessonDifferentGroups`.

### 3. Что если у студента в разных строках разное «Выполнено лаб»?

Берём **максимум** по строкам студента. ТЗ говорит «предполагается, что значение
одинаково; если нет — можно взять максимум или среднее». Максимум — потому что
он отражает «лучший достигнутый» результат и не наказывает студента за
техническую неаккуратность файла. Система при этом **не падает** (это отдельно
требует ТЗ). Тест: `TestCalculate_DifferentLabsTakesMax`. Логика —
в `Calculate`, ветка `if r.DoneLabs > agg.doneLabs`.

### 4. Подгруппа не указана — что происходит?

Трактуется как **1** (нормализация в `parser.go`, `normalizeRow`). Подгруппа в
ключ занятия не входит, поэтому влияет только на профиль студента и на поле
`subgroups` в его занятиях. Тест: `TestCalculate_EmptySubgroupDefaultsTo1`.

### 5. Студент посетил занятие чужой подгруппы — засчитается?

Да. Мы группируем занятия по `дата|время|тип|номер`, а не по подгруппе. Если в
строке студента стоит `Посещение=1` — занятие зачтено, независимо от подгруппы.
Это поведение из «завершающих заметок» ТЗ.

### 6. Дубликат строки (один студент, одно занятие — дважды) — двойной зачёт?

Нет. Посещения хранятся в карте по ключу занятия (`agg.visited[lessonKey]`), так
что повтор идемпотентен — занятие учитывается один раз. Тест:
`TestCalculate_DuplicateRowCountedOnce`.

### 7. Приоритет авто-зачёта — как реализован?

`result = agg.autoCredit || (visitPercent >= threshold && doneLabs >=
requiredLabs)`. Если хотя бы в одной строке студента стоит «Зачёт автоматом»=1,
`agg.autoCredit` становится `true`, и `result=true` **независимо** от
посещаемости и лаб. Тест: `TestCalculate_AutoCreditWins` (нули по всему — всё
равно зачёт).

### 8. Граничные значения порога — `>=` или `>`?

Строго `>=`. Студент ровно с 80% и ровно 5 лабами **получает** зачёт (ТЗ,
TC-20). Покрыто `TestCalculate_Boundaries`: 80%+5лаб → true; 100%+4лаб → false;
60%+5лаб → false.

### 9. Как округляются проценты?

`math.Round` (банковского округления **нет** — обычное «к ближайшему, .5 вверх»).
2 из 3 = 66.67% → **67**. Тест: `TestCalculate_VisitPercentRounding`. Функция
`percent()` в calculator.go; при нулевом знаменателе возвращает 0 (защита от
деления на ноль для пустого файла).

### 10. Где проверка доступа? Почему именно так?

На маршруте: `mw.Auth(d.Tokens)` затем
`mw.RequirePermission(d.RBAC, "calculate-attendance")`
([`router_attendance.go`](../backend/internal/transport/http/router_attendance.go)).
Порядок важен: без токена `Auth` отвечает **401**; с токеном, но без права —
`RequirePermission` отвечает **403**. Право выдаётся только роли admin в
миграции 00030. Это тот же middleware-стек, что и у `reports.export`/`photos.export`.

### 11. Как валидируется файл (Form Request в Laravel → что у вас)?

Цепочка проверок от «дешёвого к дорогому»:

| # | Где | Что проверяется | Ошибка |
|---|-----|-----------------|--------|
| 1 | [`handler/attendance.go:42`](../backend/internal/transport/http/handler/attendance.go) | **Размер тела** — `http.MaxBytesReader(UPLOAD_MAX_SIZE_MB)` | 413 `file_too_large` |
| 2 | [`handler/attendance.go:54`](../backend/internal/transport/http/handler/attendance.go) | **Наличие поля** `file` в multipart | 400 `invalid_file` |
| 3 | [`parser.go:63`](../backend/internal/service/attendance/parser.go) | **Сигнатура формата** — первые 4 байта `PK\x03\x04` (ZIP/XLSX magic) | 422 `invalid_file_type` |
| 4 | [`parser.go:71`](../backend/internal/service/attendance/parser.go) | **Валидная книга** — `excelize.OpenReader` реально распаковывает ZIP и парсит `xl/worksheets/` | 400 `invalid_file` |
| 5 | [`parser.go:85`](../backend/internal/service/attendance/parser.go) | **Число строк** ≤ `maxDataRows` (200 000) | 413 `too_many_rows` |
| 6 | [`parser.go:91`](../backend/internal/service/attendance/parser.go) | **Обязательные колонки** по заголовкам | 422 `missing_columns` |
| 7 | [`parser.go:99`](../backend/internal/service/attendance/parser.go) | **Каждая строка** (типы, форматы дат/времени, флаги) | 422 `invalid_row` с номером строки |

**Почему сигнатура, а не расширение?** Расширение файла (`filename.xlsx`) — это
только метаданные от клиента: пользователь может переименовать `.txt` в `.xlsx`.
Сигнатурная проверка читает первые 4 байта содержимого — это объективный признак
формата ZIP/XLSX, который нельзя подделать просто переименованием. Расширение
файла в хендлере **не проверяется** намеренно.

> `PK\x03\x04` — стандартная ZIP-сигнатура Local File Header. XLSX обязательно
> начинается с неё, так как является ZIP-архивом XML-файлов (`xl/workbook.xml` и др.).

### 12. Что считается «структурной» ошибкой файла, а что — ошибкой строки?

- Нет листа «Посещаемость» → `ErrSheetNotFound` → 422.
- Нет обязательной колонки → `ErrMissingColumns` (с перечислением) → 422.
- Битая ячейка (дата `23-09-2024`, тип `семинар`, флаг `может быть`, пустое ФИО)
  → `ErrRowInvalid` **с номером строки и причиной** → 422.

Тесты: `TestCalculate_SheetNotFound`, `TestCalculate_MissingColumns`,
`TestCalculate_InvalidRows`. Номер строки в сообщении — чтобы преподаватель/
пользователь сразу нашёл проблемную запись.

### 13. Пустой файл (только заголовки) — ошибка?

Нет. Возвращается валидный JSON с пустым массивом групп (ТЗ, TC-25). Тест:
`TestCalculate_EmptyFile`.

### 14. Где соблюдён SOLID?

- **SRP**: парсинг (`Parser`), расчёт (`Calculator`), сборка ответа
  (`ResponseBuilder`) — три отдельных класса в трёх файлах. `Service` —
  только оркестрация.
- **OCP**: чтобы добавить, скажем, CSV-источник, достаточно нового парсера,
  возвращающего `[]RawRow` — `Calculator`/`ResponseBuilder` не меняются.
- **DIP**: правила зачёта (`requiredLabs`, `threshold`) инжектятся в
  `Calculator` через конструктор из конфигурации, а не зашиты константами.

### 15. Оптимизация: нет ли лишних проходов?

Один проход по строкам файла собирает сразу всё: множество уникальных занятий,
агрегаты по студентам и (на втором, дешёвом проходе по уже агрегированным
студентам) итоги по группам. Никаких N+1, никаких запросов в БД — расчёт
полностью в памяти. Уникальные занятия собираются один раз в общую карту, а не
заново для каждого студента.

### 16. Производительность на большом файле (10 000 строк)?

Алгоритм линейный по числу строк (хеш-карты для занятий и студентов). Память —
пропорциональна числу уникальных студентов × занятий. `http.MaxBytesReader`
защищает от чтения гигантского тела в память.

### 16-bis. Большие файлы вы читаете по частям или отклоняете? Что с «xlsx-бомбой»?

**Отклоняем — на двух уровнях.**

1. **По размеру входа.** `http.MaxBytesReader` режет тело запроса на
   `UPLOAD_MAX_SIZE_MB` ещё на чтении → 413. Гигантский по весу файл просто не
   попадёт в память.
2. **По числу строк.** Это и есть защита от «бомбы»: xlsx — это zip, поэтому
   крошечный по размеру архив может развернуться в миллионы строк, и проверки
   размера тела недостаточно. После `GetRows` мы сравниваем число строк с
   потолком `maxDataRows` (200 000) **до** нормализации и при превышении
   возвращаем `ErrTooManyRows` → **413 too_many_rows**. См. `parser.go`
   (`if len(rows)-1 > maxDataRows`). Тест: `TestParser_TooManyRows` (в тесте
   лимит временно понижается, чтобы не генерировать 200k строк).

Почему не «потоковое чтение по частям» (streaming `Rows()` у excelize)? Для
учебного файла от доверенного источника (админ) это переусложнение: лимит строк
закрывает реальный риск проще и понятнее. Если бы файлы были публичными и
произвольного размера — перешёл бы на потоковый разбор с тем же лимитом.

### 17. Что с дополнительным списком `automatic_success_students`?

ТЗ (п. 8) просит отдельное поле со списком всех получивших зачёт.
`ResponseBuilder.Build` собирает плоский список `{group, name}` по всем студентам
с `result=true`, отсортированный по группе и ФИО. Назван по ТЗ-имени
`automatic_success_students`.
