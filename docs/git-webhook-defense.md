# Защита лабы №6 (git-webhook): шпаргалка

Этот документ — **как защищать**: что показать, что говорить и что у тебя
спросят. Технические детали и маппинг на баллы — в [git-webhook.md](git-webhook.md);
готовый сценарий запросов — в [git-webhook.http](git-webhook.http).

---

## 1. Суть в двух предложениях

> Это HTTP-ручка, которую дёргает git-хостинг (или curl) после пуша. Получив
> запрос с правильным секретным ключом, сервер **сам у себя** выполняет
> `git checkout` → `git reset --hard` → `git pull` (обновляет код), всё это
> логирует, и не даёт двум обновлениям идти одновременно.

Цель — **авто-деплой**: запушил в `main` → сервер сам подтянул свежий код,
без ручного захода по SSH.

---

## 2. Как это работает (поток запроса)

```
POST /api/hooks/git   { "secret_key": "..." }
        │
        ▼
 GitWebhookHandler.Handle           ← HTTP-слой: только проверка ключа
   ├─ ключ не задан в .env?         → 503 (хук выключен)
   ├─ secret_key ≠ секрета?         → 403 "Invalid secret key"  (constant-time)
   └─ ключ верный → deploy.Service.Deploy(ctx, IP)   ← оркестратор
            │
            ├─ 1) лог "started" (время, IP)
            ├─ 2) взять блокировку — занято? → 409 "Deployment already in progress"
            ├─ 3) есть ли .git? нет → 500
            ├─ 4) git checkout <branch>     → лог
            │     git reset --hard HEAD     → лог
            │     git pull origin <branch>  → лог
            │     любая упала? → лог error → снять блокировку → 500
            ├─ 5) снять блокировку (defer — и при успехе, и при ошибке)
            └─ 6) лог "finished" → 200 JSON со списком шагов
```

**Ключевая мысль для защиты:** HTTP-слой (handler) знает только про ключ;
вся логика деплоя — в сервисе, который про ключ вообще не в курсе. Поэтому
секрет физически не может утечь в лог деплоя.

## 3. Что показать преподавателю (живое демо)

### Самый простой путь — один скрипт (показывает настоящий `git pull`)

```bash
bash scripts/git-webhook-demo.sh
```

Скрипт сам поднимает Postgres + backend, создаёт во временной папке отдельный
git-репозиторий с `origin` и маркер-коммитом (твой репозиторий не трогает),
дёргает `POST /hooks/git` и показывает, что **маркер-файл реально подтянулся**
(`git pull` сделал fast-forward), печатает журнал деплоя и негативный 403.
Это — самое наглядное доказательство реального деплоя; после — всё убирается.

Ниже — как сделать то же руками, если хочешь показать по шагам.

### Подготовка (1 раз)

1. В `.env` задать ключ 36 символов:
   ```bash
   echo "GIT_WEBHOOK_SECRET=$(openssl rand -hex 18)" >> .env
   ```
2. Чтобы `git pull` реально что-то делал, пусть `GIT_REPO_PATH` указывает на
   настоящий checkout с `.git`. Проще всего — **запустить backend локально**
   (не в Docker) из корня репозитория, тогда деплой отрабатывает по-настоящему.
   > В Docker-образе `.git` нет (вкомпилён бинарь) → ручка честно вернёт 500
   > «not a git repository». Это нормально и тоже можно показать как обработку
   > ошибки, но для «зелёного» демо запускай локально на чекауте.

### Сценарий (через `git-webhook.http` в VS Code REST Client или curl)

| # | Что делаешь | Что показываешь | Код |
|---|---|---|---|
| 1 | POST с верным ключом в **JSON** | JSON-ответ: `status:success`, `branch`, список 3 шагов с выводом git | **200** |
| 2 | POST с верным ключом в **form-data** | тот же успех — приняли оба формата | **200** |
| 3 | POST с **неверным** ключом | `{"message":"Invalid secret key"}` | **403** |
| 4 | POST с ключом **в другом регистре** | тоже 403 — сравнение регистрозависимое | **403** |
| 5 | POST **без** ключа | 403 | **403** |
| 6 | Два запроса **внахлёст** (см. ниже) | один 200, другой 409 «уже идёт» | **409** |
| 7 | Убрать ключ из `.env`, перезапустить | любой запрос → «webhook is not configured» | **503** |

Параллельный запуск (пункт 6) — из терминала:
```bash
for i in 1 2; do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST http://localhost:8080/api/hooks/git \
    -H 'Content-Type: application/json' \
    -d '{"secret_key":"ВАШ_КЛЮЧ"}' &
done; wait
# Ожидаемо: 200 и 409
```

### Показать журнал

Открыть `storage/logs/deployment.log` (или вывод сервера) — там по строке-JSON
на событие:
```json
{"time":"...","ip":"10.0.0.5","stage":"started","status":"started"}
{"time":"...","ip":"10.0.0.5","stage":"command","status":"success","command":"git checkout main","detail":"Already on 'main'"}
{"time":"...","ip":"10.0.0.5","stage":"command","status":"success","command":"git reset --hard HEAD","detail":"HEAD is now at ..."}
{"time":"...","ip":"10.0.0.5","stage":"command","status":"success","command":"git pull origin main","detail":"Already up to date."}
{"time":"...","ip":"10.0.0.5","stage":"finished","status":"success"}
```
**Подчеркни:** в журнале есть дата/время, IP, каждая команда с результатом,
финал — и **нет секретного ключа**.

### Показать тесты
```bash
cd backend && go test ./internal/service/deploy/ ./internal/transport/http/handler/ -run "Deploy|GitWebhook|Lock" -v
```
13 тестов зелёные: 403/регистр/503/200/form/409 + порядок команд, ветка из
конфига, не-репо, снятие блокировки при ошибке, TTL.

## 4. Какие файлы открыть и что сказать

| Файл | Что сказать |
|---|---|
| `backend/internal/transport/http/router_deploy.go` | «Маршрут `POST /api/hooks/git` сгруппирован под префиксом `hooks`, открыт без авторизации, вынесен из 30-сек таймаута — `git pull` может идти дольше.» |
| `backend/internal/transport/http/handler/deploy.go` | «HTTP-слой: достаю `secret_key` из JSON или form-data, сравниваю **в постоянном времени** (`crypto/subtle`), маплю ошибки сервиса в 403/409/500/503. Логики деплоя тут нет.» |
| `backend/internal/service/deploy/deploy.go` | «Оркестратор: строго по ТЗ — лог-старт → блокировка → проверка `.git` → команды по порядку → снять блокировку (defer) → лог-финиш.» |
| `runner.go` | «`DeployCommands(branch)` — фиксированная тройка команд, ветка из конфига. `Runner` — интерфейс, в бою `os/exec`, в тестах подменяется фейком.» |
| `lock.go` | «`MemoryLock` — блокировка с TTL. Второй параллельный запрос получает 409. TTL страхует от зависшего деплоя.» |
| `recorder.go` | «Отдельный сервис журналирования — пишет JSON-строки в файл и в slog. Секрет сюда не доходит.» |
| `internal/config/config.go` + `.env.example` | «Все параметры через `.env`: ключ, ветка, путь, файл лога, таймаут.» |

## 5. Вероятные вопросы преподавателя (и ответы)

**— Почему POST, а не GET?**
GET положил бы ключ в URL → он осел бы в access-логах, истории браузера,
прокси. POST передаёт ключ в теле — секрет не светится.

**— Как сравниваешь ключ? Чем плохо обычное `==`?**
`crypto/subtle.ConstantTimeCompare` — сравнение за **постоянное время**.
Обычное сравнение выходит на первом несовпавшем байте, и по времени ответа
можно подбирать ключ посимвольно (timing-attack). Constant-time это исключает.
Регистрозависимо: ключ в другом регистре → 403.

**— Что если придут два запроса одновременно?**
Первый берёт блокировку, второй получает `false` → **409 "Deployment already
in progress"**. Без этого два `git pull` затёрли бы друг друга.

**— А если деплой завис и блокировку не сняли?**
У блокировки есть **TTL** (по умолчанию 5 минут): по истечении она считается
протухшей, и следующий запрос её перехватывает. Деплой не блокируется навсегда.

**— Почему секрет точно не попадёт в лог?**
Сервис деплоя его **вообще не получает** — `Deploy(ctx, clientIP)` принимает
только IP. Ключ остаётся в HTTP-слое. В журнал пишутся время, IP, команда,
статус, вывод git — секрета там нет by design.

**— Что делает `git reset --hard HEAD` и не опасно ли это?**
Отбрасывает все локальные изменения в рабочем дереве, чтобы `git pull` не упал
на конфликте. Да, разрушительно — но этого требует ТЗ (сервер-деплой не должен
хранить локальных правок; источник истины — удалённая ветка).

**— А если на сервере есть незакоммиченные/неотслеживаемые изменения?**
Перед основными командами делаю `git status --porcelain --untracked-files=all`.
Если дерево «грязное» — пишу **warning** в журнал и в JSON-ответ (поле
`warnings`), затем `git clean -fd` убирает неотслеживаемые файлы. Локальные
правки намеренно **не** stash-ятся и не коммитятся — на сервере они могут быть
случайными или подозрительными. `git clean` запускаю **без `-x`**, поэтому
gitignored-файлы (например, `.env`) не удаляются. Отслеживаемые правки
отбрасывает обязательный `git reset --hard HEAD`.

**— Почему `/api/hooks/git`, а не `/hooks/git`?**
Доступны **оба**. Основной — `/api/hooks/git` (в проде обратный прокси
проксирует на бэкенд только `/api/*`). Литеральный из ТЗ `/hooks/git` — для
прямого обращения к бэкенду (как на демо). Оба под префиксом `hooks`.

**— В каком смысле «синхронно»?**
HTTP-ответ возвращается **только после** выполнения всех трёх команд — клиент
получает финальный статус (success/ошибку), а не «принято в работу».

**— Что будет при ошибке git (конфликт, нет прав)?**
Команда логируется как `error` с выводом git, блокировка снимается через
`defer` (даже на ошибке), клиенту — **500** с описанием (без секрета).

**— Зачем проверка `.git`?**
Если каталог — не git-репозиторий, команды упали бы с непонятной ошибкой.
Заранее проверяю наличие `.git` и отдаю осмысленную 500 «not a git repository».

**— Где SOLID?**
Handler (HTTP) ⟂ Service (оркестрация) ⟂ Runner/Locker/Recorder (интерфейсы).
Single Responsibility — каждый слой про одно. Dependency Inversion — сервис
зависит от интерфейсов, а не от `os/exec`/файла (отсюда тесты без настоящего
git). Open/Closed — заменить блокировку на распределённую можно без правок
сервиса.

**— Как масштабировать на несколько серверов? `MemoryLock` же в памяти.**
Именно поэтому блокировка спрятана за интерфейсом `Locker`. Для кластера
подставляется распределённая реализация — advisory-lock в Postgres или `flock`
на общий том — без изменений в оркестраторе.

**— Почему `/api/hooks/git`, а не `/hooks/git` как в ТЗ?**
В нашей архитектуре обратный прокси (nginx/Caddy) проксирует на бэкенд только
`/api/*`. Голый `/hooks/git` в проде до бэкенда не дошёл бы. Префикс `hooks`
(требование ТЗ) соблюдён — группа `/api/hooks`.

**— Почему Go, а методичка под Laravel?**
Проект на Go+Vue; сделана эквивалентная адаптация с теми же гарантиями
(маппинг сущностей — в `git-webhook.md`, §1). ТЗ разрешает свой стек.

**— Как тестируешь, не вызывая настоящий git?**
`Runner` — интерфейс; в тестах подменяю фейком, который записывает вызванные
команды и умеет «падать» на заданной. Так проверяю порядок команд, обработку
ошибки и снятие блокировки без реального git.
