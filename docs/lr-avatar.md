# Лаба «работа с файлами» — фотография профиля

Единый документ по лабе: **что это и что требовалось**, **куда уходит результат и
как показать**, **как работает под капотом** (поверхностно — то, что препод
смотрит глазами), и **вопросы защиты с ответами** и указателями в код. Рунабельный
сценарий — [avatar.http](avatar.http).

> **Стек.** Методичка под Laravel (таблица `files`, Intervention Image, диск
> `storage/app`). Проект — Go (chi + pgx + sqlc) + Vue, поэтому реализован
> **эквивалент** на текущем стеке (в ТЗ это допускается).

---

## Что за лаба (в двух словах)

Пользователь загружает картинку профиля, сервер её **проверяет, сжимает и
хранит**, отдаёт публичную миниатюру (аватар 128×128) и защищённый сжатый
оригинал. Суть проверки преподавателя — что мы **не верим клиенту**: тип файла
определяется по содержимому, а не по имени; большой снимок ужимается; есть защита
от вредоносных изображений.

**Три акцента, которые особенно проверяют:** (1) проверка по содержимому, а не по
расширению; (2) сжатие/даунскейл больших снимков; (3) хранение сжатой копии, а не
исходных байтов.

---

## Куда уходит результат и как показать, что всё работает

В отличие от лабы №12 (где ответ — разовый JSON), здесь файл **сохраняется в БД**:
из одного снимка делаются две производные и кладутся в таблицу `user_photos`
(`bytea`). На пользователя — ровно одно активное фото (прежнее мягко удаляется).

**Как показать** — через [avatar.http](avatar.http) (REST Client в VS Code):

1. **#1 login** — токен.
2. **#2 upload** настоящей картинки (нужен файл `avatar-sample.png` рядом с
   `.http`) → **200** + `PhotoResponse` (метаданные, `avatar_url`, `download_url`).
3. **#3 — ГЛАВНОЕ ДЛЯ ЗАЩИТЫ:** отправляем обычный **текст** под именем `pic.png`
   с заголовком `Content-Type: image/png`. Сервер игнорирует имя и заголовок,
   пытается декодировать байты, не может → **415**. Это доказывает, что проверка
   по содержимому реальна и её не обойти переименованием.
4. **#5 GET** — метаданные; **#6** — публичная миниатюра (открывается как
   картинка 128×128); **#7** — скачать оригинал; **#9** — админский ZIP-архив;
   **#10/#11** — удаление и 404 после него.
5. **Проверка доступа:** **#12** без токена → 401; **#13б/#13в** обычным
   пользователем на `/api/photo/all` и `/api/photo/archive` → 403 (нужно право
   `photos.export`).

## Как это работает под капотом (поверхностно)

Пайплайн загрузки: `POST /api/photo` → `MaxBytesReader` (≤16 МБ тела) →
`imageutil.Process` → в одной транзакции {мягко удалить прежнее фото, вставить
новое, записать в `change_logs`} → ответ с метаданными.

**Главный файл — [`imageutil.go`](../backend/internal/imageutil/imageutil.go),
функция `Process`.** Порядок проверок намеренно «дешёвое → дорогое»:

1. **Пустой файл** → `ErrEmpty`.
2. **Заголовок без распаковки** — `image.DecodeConfig`: читает сигнатуру формата
   (анти-спуфинг) и габариты. Если не картинка → `ErrNotImage`.
3. **Лимит пикселей ДО декода** — `if width*height > MaxPixels (40 Мп)` →
   `ErrTooLarge`. Это защита от «бомбы»: крошечный по байтам PNG может
   развернуться в гигапиксели; мы режем по габаритам из заголовка, **не
   распаковывая** в память.
4. **Полная распаковка** — `image.Decode`. Любая ошибка здесь — тоже признак
   подделки/битого файла.
5. **Сжатие** — `downscaleToFit`: снимок крупнее `MaxStoredDimension` (1600 px по
   большей стороне) ужимается с сохранением пропорций.
6. **Кодирование** — `encode`: PNG если есть прозрачность (альфа-канал), иначе
   JPEG (q82). Формат выбирается по свойствам картинки.
7. **Аватар** — `squareThumbnail`: центрированный квадрат → 128×128.

**Сервис** [`photo/service.go`](../backend/internal/service/photo/service.go) —
лимит размера входа (`MaxUploadBytes` = 16 МиБ), транзакция, soft-delete прежнего
фото, логирование. **Хендлер**
[`photo.go`](../backend/internal/transport/http/handler/photo.go) — multipart,
понятные сообщения об ошибках.

> Расширение файла **не проверяется вообще** — намеренно (см. вопрос 2).

## FAQ — вопросы защиты и ответы

### 1. Как определяете, что это действительно изображение, а не переименованный файл?

По содержимому. `imageutil.Process`: `image.DecodeConfig` читает сигнатуру
(магические байты), затем `image.Decode` распаковывает в пиксели. Текст/exe с
расширением `.png` не образует валидной структуры → ошибка → **415**.

> **Ключевая фраза:** «Расширению и Content-Type от клиента верить нельзя.
> Единственная честная проверка — реально декодировать байты как изображение.»

### 2. А расширение файла вы проверяете?

**Нет — намеренно.** В пути загрузки фото нет сравнения `.png/.jpg` (можно
показать, что в `photo.go`/`service.go` его нет). Расширение ничего не доказывает;
формат хранения мы определяем сами по результату декода, имя сохраняем только как
метаданные (`sanitizeName`). Если внутри настоящая картинка с «неправильным»
именем — примем; цель — отсечь не-картинки.

### 3. Зашифрованный или битый `.png` пройдёт?

Нет. Не образует валидный JPEG/PNG/WebP-поток → `DecodeConfig`/`Decode` падает →
**415**.

### 4. Что с большим снимком (4K)? Где сжатие?

`downscaleToFit`: больше 1600 px по большей стороне → даунскейл с пропорциями
(`draw.CatmullRom`) + перекодирование. Хранится сжатая копия. Пример:
`4000×3000, 274 КБ → 1600×1200, 42 КБ` (≈6.5×).

### 5. JPEG или PNG на выходе? Почему не всегда JPEG?

`preferPNG := !isOpaque(src)`. JPEG не умеет прозрачность: есть альфа → PNG (без
потерь), нет → JPEG (сильнее жмёт). Формат по свойствам картинки, не вслепую.

### 6. Защита от «бомбы» (крошечный файл — гигантское разрешение)?

`MaxPixels = 40_000_000`. Габариты читаются из заголовка (`DecodeConfig`) и
сравниваются **до** полной распаковки. Гигапиксельный PNG не доходит до декода →
**413**. Почему до декода — если распаковать сначала, атака уже съест память. Тест
`TestProcess_RejectsPixelBomb`.

### 7. По весу файла лимит есть?

Да, две разные границы: по весу тела — `MaxBytesReader`/`MaxUploadBytes` (16 МиБ)
→ 413; по разрешению — `MaxPixels` (40 Мп) → 413. Это разные атаки, закрыты по
отдельности.

### 8. Где хранятся файлы и почему нет прямого URL у оригинала?

В БД (`bytea`), не на диске. Хранятся две производные. Оригинал отдаётся **только
владельцу** через `GET /api/photo/download` (проверка `userID` из токена). Аватар
публичный — тег `<img>` не умеет слать Bearer.

### 9. Сколько фото на пользователя? Что при повторной загрузке?

Одно активное. В `Upload` в одной транзакции: soft-delete прежнего → вставка
нового → запись в `change_logs`. История сохраняется через `deleted_at`. `Delete`
идемпотентен (повторный DELETE без фото — не ошибка).

### 10. Действия с фото логируются?

Да — `photo_uploaded`/`photo_deleted` в `change_logs`, в той же транзакции. В
историю кладутся метаданные (имя/формат/размер), не байты.

## 🔴 Где могут прижать

1. **EXIF-ориентация.** Фото «боком» с некоторых телефонов не поворачивается:
   декодер Go не применяет EXIF-orientation. Для прода — читать тег и поворачивать.
   На проверки не влияет.
2. **Почему не `http.DetectContentType`?** Это «sniff» 512 байт, обходится
   PNG-магией в начале мусора. Полный декод строже.
3. **WebP только на входе.** Храним JPEG/PNG; WebP декодируется
   (`_ "golang.org/x/image/webp"`), но не хранится — два формата проще.
